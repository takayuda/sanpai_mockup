# 産廃DXシステム モック（第1期）

産業廃棄物 中間処理業者向け「産廃予約管理システム」の画面モックです。
エンジニアへの受け渡し（要件を詰めながら実装する）ことを目的としています。

## 受け渡すファイル

**`sanpai-mock.html` の1ファイルだけ**です。ブラウザで開くだけで動きます（ビルド不要）。
処理業者の管理画面と排出者ポータルの両方が入っていて、ヘッダー右上の **MOCK** ラベル付き
ボタンで排出者側に切り替わり、右下のボタンで管理画面に戻ります。

Bootstrap 5.3.3 と Google Fonts を CDN から読み込むため、初回表示にはインターネット接続が必要です。

| ファイル | 役割 |
| --- | --- |
| `sanpai-mock.html` | **配布用の単一ファイル**（処理業者 管理画面＋排出者ポータル） |
| `emitter-portal.html` | 排出者ポータルの原本。いただいたワイヤーフレームのまま。上のファイルに同梱される |
| `parts/` | 処理業者 管理画面のソース（HTML/CSS＋画面ごとのJS） |
| `build.py` | `parts/` と `emitter-portal.html` から `sanpai-mock.html` を生成する（`python3 build.py`） |

排出者ポータルは `iframe` で同梱しているため、両者のCSS・JSは干渉しません。
排出者側は原本のコードがそのまま動きます。

## データ構成（ER図との対応）

添付のER図（`companies` / `plants` / `items` / `units` / `pickups` / `pickup_items`）に準拠。
画面上のラベルは日本語に読み替えています。

| テーブル | 画面での呼び名 | 主な項目 |
| --- | --- | --- |
| companies | 取引先 | 取引先名／フリガナ／排出事業者・運搬業者の区分／担当者／メールアドレス（ログインID）／電話番号／郵便番号・都道府県・住所／インボイス登録番号／振込先口座／与信区分／登録状態 |
| plants | 拠点 | 拠点名／持込受入の可否／引取対応の可否／引取対応時間／住所・電話番号 ＋ 受入時間枠（複数）・定休日・臨時休業日・予約の締切 |
| items | 品目 | 品目名／廃棄物区分／有価物 |
| units | 単位 | 単位（kg・t・m3・個・台・袋） |
| pickups | 予約・実績 | 受付番号／取引先／拠点／区分（持込・引取）／日付／開始・終了時刻／ステータス／伝票番号／着車時間／正味重量／申告との差異／計量時の備考／承認日時／取消日時・取消理由 ＋ 車両ナンバー（持込）・引取場所（引取） |
| pickup_items | 予約明細 | 品目／単位／申告数量（計量後は「実際に含まれていた品目」の一覧になる） |

補足:
- ER図の `receipt_number` は「当日の計量伝票番号」として入場受付時に採番します。
  取引先に案内する受付番号（`R-2026-0158` 形式）は排出者ポータルに合わせ申請時に採番します。
- `password` / `remember_token` は取引先が本登録時に設定するため、管理画面には表示しません。
- 重量はすべて kg（整数）で保持します。
- ER図の `total_weight`（総重量）／`car_weight`（空車重量）は第1期では使いません。構内では
  品目ごとの計量ができないため、記録するのは**総正味重量と、含まれていた品目**だけです。
- **着車時間**は、持込・引取のどちらも「自社拠点に車両が到着した時刻」です。引取の場合は
  集荷から戻ってきた時刻を指します。
- **1予約＝1車両**です。複数台で搬入する場合は台数ぶん予約を作成します（台数の項目はありません）。
- 引取の集荷先（現場名・住所）は `pickups` にテキストで保持しています。ER図に排出現場の
  マスタがないためで、現場マスタを持つかは要検討です。

## 取引先の新規登録フロー

```
① 取引先マスタに表示されている登録用URLを取引先担当者へ送る
② 取引先が URL から本登録（社名・区分・連絡先・メールアドレス・パスワード）
③ 以降、そのアドレスでログインすると当該処理業者への予約が作成できる
```

登録用URLは処理業者ごとに**1本を使い回します**（何社でも登録可）。社内では取引先の情報を
一切入力しません。URLが外部に漏れたときなど必要な場合のみ「URLを再発行」でき、再発行すると
旧URLは無効になります（確認チェックを挟みます）。取引先が本登録を完了した時点で、
はじめて取引先一覧に追加されます。

取引先が処理業者を検索・選択する画面は設けません。招待された処理業者だけが取引先側に表示されるため、
取引先が本システムの導入企業を一覧できることはなく、選択で迷うこともありません。

## 動かして確認できる業務の流れ

データはすべてブラウザ内のダミーです。リロードすると初期状態に戻ります。
日付は開いた日を基準に相対生成されます。

1. **承認キュー** で `R-2026-0158`（持込）を承認（受入時間枠を調整可）。
2. `R-2026-0152`（引取）を承認 → 訪問日時の確定入力が必須。集荷手配メモも記録できる。
3. `R-2026-0172` を「変更依頼」→ 理由必須・代替候補の提示を確認。
4. **予約一覧ボード**（本日）で、持込の「枠変更」、引取の「日時変更」を実行。
5. **計量入力** で「計量入力」→ 着車時間（既定は現在時刻）・総正味重量・含まれていた品目・備考を記録。
   申告数量（重量換算）との差異がその場で表示され、確定すると伝票番号が採番されます。
   受入できなかった場合は、モーダル左下の「受入不可として記録」から記録します。
6. **実績一覧** で差異を確認し、CSV出力。
7. **受付時間・休業日** で受入時間枠の追加／削除、引取対応時間の変更、予約の締切（既定：前日17時）、
   臨時休業日の登録。持込受入・引取対応の切替は、影響の確認とチェックを求める確認画面を経由します。
8. **取引先** の登録用URL →「登録画面を開く」で取引先側の本登録まで確認。
9. ヘッダーの「排出者側の画面」で、取引先から見た予約フローを確認。

## 確認したい論点

| # | 論点 | モックでの扱い | 確認したいこと |
| --- | --- | --- | --- |
| 1 | 受付番号の採番タイミング | 申請時に採番（排出者ポータルに合わせた） | 仕様書は「承認時に採番」。どちらに寄せるか |
| 2 | 引取の希望時間 | 開始・終了の希望時刻を受け付け、承認時に確定時刻を返答 | 「午前／午後」の選択にする案もある |
| 3 | 受入時間枠の粒度 | 拠点ごとに複数設定（既定は午前・午後の2枠） | 1時間刻みの要望があるか。拠点ごとでよいか |
| 4 | 上限管理 | 受付上限は設けない | 将来的に上限が必要になる場面があるか |
| 5 | 1台に複数品目 | 品目ごとの計量はできないため、総正味重量と「含まれていた品目」だけを記録 | 品目別の数量が必要になる場面があるか（あれば按分ルールの検討が必要） |
| 6 | 新着通知 | 画面内の通知のみ | LINE／LINE WORKS／メールのいずれか。運用可否を左右するため優先確定 |
| 7 | 登録用URL | 1本を使い回し、必要時のみ再発行 | URLを知っていれば誰でも登録できる。本人確認（申込の承認、ドメイン制限など）が必要か |
| 8 | 複数処理業者からの招待 | 未実装（1社からの招待のみ） | 取引先が複数の処理業者を持つ場合のログイン後の選択画面 |
| 11 | 予約の締切 | 拠点ごとに「◯日前の◯時」で設定（既定：前日17時）。過去日は作成・承認とも不可。締切後も社内からは登録でき、その旨を注意表示 | 締切を過ぎた予約の取消・変更をどこまで社内に許すか |
| 12 | 稼働設定の変更と既存予約 | 定休日・対応時間を変えても既存予約はそのまま残る | 変更時に該当予約を一覧化して連絡を促すか |
| 13 | 計量の単位 | 差異は kg・t で申告された分のみ算出（m3・個・台は対象外） | 体積申告の実務上の扱い |
| 14 | 与信区分・振込先口座 | 取引先マスタに項目はあるが使い道がない（売上機能なし） | 第1期で保持するか、項目ごと落とすか |
| 9 | 拠点 | 2拠点を用意し、ヘッダーで切替 | 第1期は単一拠点想定でよいか |
| 10 | 認証・ログイン | 未実装 | 認証方式 |

## 排出者ポータルと管理画面のデータ構造の差異

同じ業務を扱う2つの画面ですが、モックとしては別々のダミーデータで動いています。
実装時に揃える必要がある点は次のとおりです。

| # | 項目 | 排出者ポータル | 処理業者 管理画面 | 対応方針の案 |
| --- | --- | --- | --- | --- |
| 1 | 拠点 | 処理業者を選ぶだけ（拠点の概念なし） | 予約は必ず拠点に紐づく | 第1期を単一拠点に限定するか、排出者側に拠点選択を追加する |
| 2 | 品目・単位 | 文字列（`廃プラスチック類`）で保持 | マスタのID（`i1`）で保持 | 排出者側もマスタIDで受け渡す |
| 3 | 車格 | 持込時に必須入力 | 保持していない | 上限管理をしない第1期では不要か、記録だけ残すか |
| 4 | 引取場所 | 現場マスタ＋住所の直接入力＋「現場マスタに登録」 | テキストで保持（現場マスタなし） | 排出現場マスタを持つか、テキストのままにするか |
| 5 | 受入時間枠 | 9:00〜12:00／13:00〜16:00 の固定 | 拠点ごとに可変（川口ヤードは8:30〜11:30／13:00〜17:00） | 排出者側は拠点の設定を読んで表示する |
| 6 | 受付停止日 | 固定のダミー判定 | 定休日＋臨時休業日 | 同上 |
| 7 | 予約の締切 | 未実装 | 拠点ごとに設定（既定：前日17時） | 排出者側でも締切後は選べないようにする |
| 8 | 品目ごとの備考 | 品目行ごとに入力できる | 予約単位の連絡事項のみ | `pickup_items` に備考を持たせるか |
| 9 | ステータス表記 | 申請中／承認済（予約確定）／差戻し | 申請中／承認済／差戻し／計量済／取消 | 表記を統一する |
| 10 | 受付番号 | 申請時に採番 | 同左（ER図の `receipt_number` は当日の伝票番号として別管理） | 採番タイミングを確定する |

今回の修正で、**ドライバー名・連絡先の廃止**と**1予約＝1車両（台数なし）**は両画面で揃えました。

## 第1期に含まないもの（モックにもありません）

- 売上・会計（売上明細、請求書、月次締め、会計CSV）
- 配車ボード＝車両・ドライバーの割当編成、運行指示書出力、地図表示、ルート最適化
- 受付上限の設定（着車数・処理量・品目別・引取件数）
- 権限（ロール）による画面の出し分け
- 監査ログ
- 入場受付（着車の記録は計量入力にまとめています）
- マニフェスト管理・JWNET連携
- 契約・単価マスタ、コンテナの在庫・配置管理、構内工程管理

引取については、第1期のシステムの役割は「集荷依頼を受け、承認し、訪問日時を返し、集荷実数を記録する」までです。
集荷手配そのものは台帳・電話などの既存手段で行い、モックでは「集荷手配メモ」欄に記録するだけにしています。

## 技術メモ（実装担当者向け）

- Bootstrap 5.3.3（CDN）＋素の JavaScript。ビルドツール・フレームワークは使っていません。
- 配色・角丸・タイポグラフィは排出者ポータルのトークンを Bootstrap の CSS 変数に上書きして揃えています。
- アイコンはインラインSVG（線画）を `ICONS` に定義し、`ic('名前')` で描画。
- 構造は「状態（`state`）→ `render()` で画面全体を描き直す」という単純な形です。
- ダミーデータは `parts/02_data.js`（出力ファイルでは前半）に集約。過去45日ぶんの実績は
  固定シードの疑似乱数で生成しているため、開くたびに同じ内容になります。
- 主要なロジック:
  - `isClosed()` / `countOf()` / `slotOf()` … 稼働日・時間枠の判定
  - `declaredKg()` … 申告数量の重量換算（kg・t のみ換算。差異の算出に使用）
- 状態はメモリ上のみでの保持です。永続化・API・認証は未実装です。
